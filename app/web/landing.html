On-call triage that remembers

OnCallAI turns a CloudWatch or Datadog alarm into a diagnosis from the logs that fired it. Then it asks MIND which past incidents are connected, and keeps the confirmed root cause for the next person on call.

What happens when an alarm fires

Five steps, in order. The first three use only what is happening now. Memory comes fourth, so it can inform the diagnosis without replacing it.

  1. The alarm arrives

    From CloudWatch through SNS and SQS, or from a Datadog monitor webhook. If OnCallAI is down, alarms wait in the queue.

  2. The logs are pulled

    The lines from the minutes before the alarm, from the failing service and the services it calls.

  3. A diagnosis from today's logs

    Rules and retrieval over those lines. This is the root cause the report leads with.

  4. Memory is checked

    MIND returns related past incidents. Each one counts only if today's logs show the same failure.

  5. The confirmed cause is kept

    When an engineer confirms what actually happened, it goes back to MIND, linked to the services involved.

Similar text is not the same as connected

The same new checkout incident, looked up two ways. Text search asks what reads like this alarm. A graph walk asks what is connected to the services in it.

Text similarity

What reads like “elevated error rate, latency spike, HTTP 504”?

  • lookalikeInventory memory leak. Same words in the alert, unrelated service.
  • by chancePayment gateway timeout. Found because both mention timeouts.
  • missedCheckout errors caused by payment slowness, the closest relative.

Relationship walk

What touches checkout-service or what it calls?

  • connectedCheckout errors caused by payment slowness. Same service.
  • one hopPayment gateway timeout, reached through checkout calling payment.
  • left outInventory memory leak. Nothing links it to checkout.

Three rules the memory follows

Memory that is wrong is worse than no memory. These keep it honest.

Today's logs lead
History adds leads and checks to try. It never replaces the root cause found in current evidence, and it never raises confidence on its own.
Only confirmed causes are stored
The triage guess is never written back. An engineer confirms what happened, so memory does not learn its own mistakes.
Triage never waits on memory
If MIND is slow, down, or returns something unexpected, the incident is triaged exactly as before and the report says so.

Alert sources

Both feed the same pipeline. Neither needs an agent on your servers.

AWS CloudWatch

Alarm to SNS to SQS. OnCallAI pulls from the queue, so it runs on a laptop with no public URL, then reads CloudWatch Logs for the window before the alarm.

# creates log groups, metric filter, alarm, topic, queue
bash scripts/aws_demo_setup.sh
export CW_SQS_QUEUE_URL=https://sqs...
python3 scripts/aws_emit_logs.py

Datadog

Point a monitor webhook at OnCallAI. With an API and application key, it also pulls the matching logs through the Logs Search API.

# Integrations, Webhooks, New
URL      https://your-host/api/webhooks/datadog
Payload  {"title": "$EVENT_TITLE",
          "transition": "$ALERT_TRANSITION",
          "tags": "$TAGS", "date": "$DATE", ...}

Run it in a minute

No cloud account needed for the first look. A recorded CloudWatch alarm runs through the same code a real one would, and MIND is simulated until you add a key.

Open the console 
./scripts/start.sh                 # checks, tests, starts
# real MIND
MIND_ENABLED=true MIND_API_KEY=mind_... ./scripts/start.sh
# real CloudWatch
CW_SQS_QUEUE_URL=https://sqs... ./scripts/start.sh
